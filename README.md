# Errand Agent

A chat agent that arranges home-service errands (plumber, electrician, AC servicing, …): it asks only
for missing details, compares providers, **asks for approval in code before anything consequential**,
books idempotently, recovers from timeouts/crashes using the provider's source of truth, remembers
preferences with provenance, follows up proactively when a provider cancels — and traces every step.
Everything runs locally against mock providers; there are no real payments or external services.

```
python -m pytest                          # 74 tests incl. 34 eval scenarios -> reports/eval_table.md
python -m errand_agent.web --reset        # demo UI: chat | live trace  ->  http://localhost:8765
python -m errand_agent.cli --reset --show-trace
```

No runtime dependencies (Python ≥ 3.9, stdlib + SQLite). `pytest` for tests.
On macOS/Linux the command is usually `python3` (use it everywhere below instead of `python`).

## Run it with a real LLM (Groq free, or xAI Grok)

The adapter (`errand_agent/llm/openai_compat.py`) speaks the OpenAI-compatible API, so no SDK is needed.

1. Get a key — **Groq** is free with no card: <https://console.groq.com/keys>. **xAI Grok** is paid:
   <https://console.x.ai>.
2. Copy `.env.example` to `.env` in the repo folder and paste the key (`GROQ_API_KEY=...` or `XAI_API_KEY=...`).
3. Check the key and tool calling:
   ```
   python -m errand_agent.check_llm --model groq      # or --model grok
   ```
4. Run the demo (chat on the left, live trace on the right):
   ```
   python -m errand_agent.web --model groq --reset    # or --model grok
   ```
   then open <http://localhost:8765> and try *"Find a plumber for my kitchen tap this week, mornings only,
   under ₹1,500."* → reply **yes**. The default `timeout` preset makes the first booking time out after
   succeeding, so you can watch the recovery in the trace.

Defaults: Groq `openai/gpt-oss-120b`, Grok `grok-4-1-fast-non-reasoning`. If your key cannot use the configured model, the adapter lists the models your key can use and switches to a tool-capable one automatically (`check_llm --list` shows them). Pick another model with
`--model groq:<model-id>` / `--model grok:<model-id>` or `GROQ_MODEL` / `GROK_MODEL` in `.env`. Any other
OpenAI-compatible endpoint: `--model openai-compat` with `ERRAND_BASE_URL`, `ERRAND_API_KEY`, `ERRAND_MODEL`.
Claude: `pip install anthropic`, set `ANTHROPIC_API_KEY`, use `--model anthropic`.
Add `--record data/cassette.jsonl` to record model calls for strict offline replay.

The automated tests never call an API — they use the offline scripted model, so `pytest` works without a key.

## How it works (short)

* **Model drives, code decides.** The model gets 10 tools: `update_request`, `search_providers`,
  `get_provider`, `list_bookings`, `propose_booking|reschedule|cancel`, `remember`, `forget`,
  `show_memories`. The side-effecting contract tools (`hold_slot`, `book`, `cancel`, `reschedule`) are
  only called by the app's executor after `ApprovalGate.authorize()` passes.
* **Approval** is a DB row created only when the user's *next* message is a plain confirmation of the
  app-rendered card; it is bound to a hash of provider/slot/quoted price (or booking id) and is single-use.
* **Booking correctness** — durable intent ledger + one idempotency key per target, written before
  `book()`; timeouts resolved by `get_booking_status`; startup and per-turn reconciliation.
* **Untrusted output** — reviews are sanitised and flagged; request changes and memory writes need a
  verbatim quote from the user's own message; a claim guard blocks unverified "booked!" text.
* **Memory** — explicit vs inferred (unconfirmed inferred facts never reach the model), inspect /
  correct / forget (forget scrubs stored history too).
* **Context** — fixed token budget on the real payload, relevance-ranked memories, newest-first
  history, per-call manifest in the trace.

See `DESIGN.md` for the state model, recovery rules and trade-offs.

## Tool environment (mocks)

`errand_agent/mocks/service.py` implements the fixed contracts with seeded randomness
(`ScenarioConfig`) and optional JSON persistence so the "external" service survives an agent restart.

| Tool | Mock behaviour |
|---|---|
| `search_providers(service, area, date_range)` | 3–8 providers with id, price, rating, slots, attributes |
| `get_provider(provider_id)` | details, availability, free-text reviews; `PRV-PLB-03` and `PRV-ELE-03` carry a prompt-injection review |
| `hold_slot(provider_id, slot)` | 10-minute hold, hold id + expiry; quoted price can differ (`hold_price_deltas`, `random_price_drift`) |
| `book(hold_id, idempotency_key)` | 70% success / 15% `slot_taken` / 15% timeout (half actually booked); `hold_expired` past expiry; forced outcomes via `book_outcomes`; idempotent per key |
| `get_booking_status(hold_id or idempotency_key)` | source of truth; `status_overrides` can force `pending` |
| `cancel(booking_id, idempotency_key)` | first call per booking raises 503, retry succeeds |
| `reschedule(booking_id, slot, idempotency_key)` | `slot_conflict` on configured slots |
| `list_bookings(user_id)` | past + upcoming bookings |

Test hooks (not tools): `simulate_provider_cancellation`, `take_slot_externally`, failure injection
(`inject_failures`, `always_fail`: `503`, `500`, `timeout`, `crash`), per-tool latency.

## Evals

`evals/scenarios.py` holds 34 scenarios (conversation, adversarial input, prompt injection with an
honest and a *compromised* model, price/slot change after approval, timeout after success, slot
conflict, repeated confirmation, restart mid-booking, proactive cancellation, memory
correction/forgetting/inspection, context budget, limit exhaustion, tool failures). Users are simulated
(`SimulatedUser` answers only what is asked and records any re-asked fact). Each scenario asserts
outcomes against tool-call logs, the ledger, the mock service state and the exact context payloads,
plus 7 global invariants. `tests/test_units.py` includes mutation tests showing the invariants fail
when the approval gate is bypassed or a success claim is faked, and a record → strict-replay test.

Offline evals use `RuleModel` (`errand_agent/llm/rule_model.py`), a deterministic stand-in that sees
exactly what a real model sees (system prompt with `<state>`/`<memories>`, messages, tool results) and
can be switched into misbehaving modes (`compromised`, `loop`, `claim_success`).

## Honest limitations

* The real-LLM adapters (Groq/Grok via `OpenAICompatModel`, Claude via `AnthropicModel`) are unit-tested
  against stubbed HTTP/SDK responses, including a full booking turn, but this build environment had no
  access to those APIs, so no live run or real-model cassette is included. The committed demo video
  shows the offline model; `docs/DEMO.md` is the script for recording the Loom with `--model groq`.
* Smaller open models (e.g. Llama on Groq) sometimes paraphrase instead of quoting the user for
  `evidence`; the app then rejects the change and tells the model the exact message to quote, so it
  usually corrects itself on the next step. Safety does not depend on the model getting this right.
* Token counts for the offline model are estimates (chars/4); real runs log the API's usage numbers.
  The context budget covers system + messages; tool schemas (~900 tokens) are a fixed extra.
* Forget-scrubbing is token based (value, original statement, proper nouns); a paraphrase with no
  shared distinctive token could survive (see BUG-2).
